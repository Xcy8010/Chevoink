# Outlines and chapter details

[中文](./novel-outline-plans.md)

An outline owns the book's main plot, phases, major turns and ending direction. A detail plan turns that intent into one chapter's actions, conflict, outcome, characters, setting, foreshadowing and transitions. Authors can refine detail plans progressively; planning does not authorize writing chapters or require detailing the entire book in advance.

Manual creation and the Agent's `plan_save` accept `planKind=outline|detail`. Existing untyped plans remain `legacy`, with their original content and compatibility behavior. Typed plans retain their real IDs, including identically named outlines and details. Legacy title deduplication remains unchanged. Agent title fallback matches the same kind, parent and target only; multiple typed matches require an explicit ID. Durable tasks must still read and explicitly identify an existing artifact before modifying it.

An unlinked detail draft may be saved. Execution requires an available outline in the same book and a single real chapter ID, or a future whole-book ordinal: `target={kind:'future',targetOrderIndex}`. Existing chapters use `target={kind:'chapter',chapterId}`. Missing, archived or foreign identities are never replaced by guessing an ordinal. Distant future planning does not widen the original task's chapter creation scope.

Linking requires the observed `expectedParentPlanHash`. `reviewState=current` means the parent version matches; it is not a semantic review. Editing an outline makes linked details `stale`; hiding or changing its type makes them `missing_parent`, without deleting the details. Reads never refresh the stored parent version. Explicit review and relinking are required.

`planHash` covers content, kind, parent ID, observed parent hash and target. Titles, order and timestamps are display fields and do not affect it. Semantic changes to typed plans require `expectedPlanHash`. The existing book lock and conditional updates reject concurrent overwrites. Explicit legacy conversion also requires the current hash. Task observations, approvals, revision checks, cancellation and durable receipts remain in force.

Chapter PREPARE selects a valid detail within the original authorized target. Multiple details require `detailPlanId`. A book with a typed outline requires a valid detail for the selected chapter before execution. Full outline/detail content, IDs, hashes and target are frozen in `preparedContext.planContext`. Preparation and chapter-bridge reads return full plans; scenes retain that dependency. Chapter creation upgrades a frozen future target to its real chapter ID in the same transaction and updates that compilation's snapshot. Later reordering does not rematch the detail. Scene saves, manuscript effects, commit and completion reads check the current dependencies. Historical compilations without a frozen plan context retain their original contract. After plan changes, read-only recovery summaries show that review is needed and retain read/reprepare access; old chapter completion is unavailable for reuse. Writes and commit still reject stale dependencies. Fresh Agent plan creation requires an explicit kind; only authenticated pre-existing frozen operations retain legacy creation compatibility through their original receipt path.

The existing continuity request includes versioned `planAlignment`, using its existing provider, authorization and accounting:

- `outline_to_detail` checks this chapter's outline obligations against its detail. Omissions cite the outline; contradictions cite both plans.
- `detail_to_chapter` checks the detail against the manuscript. Omissions cite the detail; contradictions cite plan evidence and a real current-chapter `sourceId`.

Only obligations explicitly assigned to this chapter or phase apply. Later plot events are not omissions in the current chapter. Unclear applicability remains `unknown`. Plans are intent, never previous-chapter facts or automatic factual memory. Reports bind frozen plan hashes and manuscript revisions. Missing, old, incomplete or invalidly cited responses cannot become `reviewed`. Valid findings enter the existing review decision flow; retaining advice does not mean it was repaired.

When the original request requires continuity review, plan alignment also needs a valid result. An author's original review waiver does not acquire a new mandatory paid check: dependency versions remain enforced and semantics remain unverified. The implementation guarantees ownership, version and reference checks and execution boundaries, not the absence of every literary contradiction or omission.

This reuses `AgentArtifact.metadata` and `StoryCompilation.preparedContext`, without a migration. Unit regressions cover compatibility, hashes, parent versions, title identity, target ownership, frozen dependencies, future binding and both evidence stages. PostgreSQL regressions cover persistence, concurrent saves and compiler dependencies; run them only against a validated isolated database. The four gates, zero-skip PostgreSQL integration, Agent eval and both dependency audits still require CI at the same SHA.
